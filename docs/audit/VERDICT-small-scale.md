# Вердикт: приоритизация под реальный масштаб

**Дата:** 2026-08-02
**Ветка:** `codebase-analysis`
**Статус:** дополнение к аудиту. Ничего из разделов A–G не отменяет и не удаляет — только переупорядочивает по фактическому риску.

---

## Контекст, под который сделана эта приоритизация

| Параметр | Значение |
|---|---|
| Профиль нагрузки | несколько сотен заказов в сутки |
| Средний параллелизм | ~1 запрос в несколько минут; пики — единицы одновременных |
| Продукт | лёгкие баркоды (быстрая генерация, малый вес) |
| Размер проекта | небольшой, малая команда |

**Почему это меняет выводы.** Разделы A–G оценивали дефекты по внутренней серьёзности: «может ли это в принципе привести к потере денег / данных / доступности». Такая оценка не учитывает **вероятность срабатывания**. Большинство пунктов раздела A (гонки) и часть B/G (exactly-once, DLQ, Redis под сбоями) требуют для проявления параллелизма и потока, которых при сотнях запросов в сутки нет. Они остаются валидными, но их ожидаемый ущерб на этом масштабе близок к нулю.

**Ключевой принцип этого файла:** дефекты **логики, денег и доступа** болят одинаково при любом трафике. Дефекты **конкурентности и пропускной способности** — только при росте. Поэтому первые идут в «сейчас», вторые — в «при росте».

## Блок 3. Осознанно отложить до роста

Валидные дефекты с низкой вероятностью срабатывания на текущем профиле. **Не «неправильные» — просто не окупаются сейчас.**

| Кластер | Пункты | Когда станет актуально |
|---|---|---|
| Гонки и конкурентность | большинство раздела [A](A-concurrency-races.md) | При устойчивом параллелизме (десятки одновременных запросов) |
| Лок и TTL под параллелизмом | [G-01](G-dlq-replay-redis.md), [G-02](G-dlq-replay-redis.md)/[A-03](A-concurrency-races.md), [A-02](A-concurrency-races.md) | Когда один пользователь реально начнёт править заказ из двух сессий |
| DLQ / replay | [G-03](G-dlq-replay-redis.md)–[G-06](G-dlq-replay-redis.md), [B-10](B-idempotency-exactly-once.md) | При объёмах, где потеря батча дороже ручного разбора |
| Наблюдаемость денежного пути | [F-04](F-operations-observability.md), [F-06](F-operations-observability.md) (трейсинг, метрики саги) | Когда разбор жалобы вручную станет дороже инструментирования |
| Пропускная способность / перф | не аудировалось отдельно | При росте на порядок |

**Важно:** отложить — это решение, а не забывание. Если проект вырастет по трафику на порядок, блок 3 переходит в блок 1 практически целиком, потому что вероятность срабатывания растёт нелинейно.

## Что аудит сказал о качестве проекта

Отдельно от списка дефектов — оценка самой кодовой базы:

**Сильные стороны (подтверждено трассировкой):**
- Чистое разделение слоёв: `domain` не зависит от инфраструктуры, протечек абстракций не найдено
- Ports/adapters проведены последовательно, а не декларативно
- Сага с компенсацией на денежном пути **спроектирована осознанно** — большинство найденных дефектов в ней это дефекты реализации деталей, а не ошибочная модель
- Идемпотентность заложена изначально, а не прикручена после инцидента
- Тесты есть почти во всех пакетах (исключение — `internal/app`)

Это уровень «инженер понимал, что делает». Количество найденных пунктов отражает **глубину аудита**, а не низкое качество кода: при такой же плотности проверки сопоставимый список найдётся в большинстве production-сервисов.

**Слабые стороны:**
- Fail-open по умолчанию — самая системная проблема (`R2`)
- Нет ворот верификации: `go build` не в проверке, CI отсутствует (`R5`) — прямая причина того, что несобирающийся HEAD доехал незамеченным
- Граница адаптеров нетипизирована (`R1`) — ошибка теряет структуру на входе

## Итог

**Реальных «чинить сейчас» пунктов — примерно 6–8, а не 106.** Все они про безопасность и корректность денег, ни один — про нагрузку. Объём: день-два, потому что половина закрывается одним фиксом fail-closed конфигурации.

Остальные ~100 находок валидны и задокументированы, но на профиле «несколько сотен лёгких баркодов в день» их ожидаемый ущерб низкий. Полные разборы сохранены в разделах [A–G](README.md) без изменений — этот файл только задаёт порядок.

**Не следует читать число 106 как «проект плохой».** Архитектура добротная; проблема сосредоточена в двух местах — конфигурация открывается наружу при отсутствии переменных, и нет ворот, которые бы это ловили.
