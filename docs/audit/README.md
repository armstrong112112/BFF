## Общие корни (первопричины)

115 пунктов — не 115 независимых ошибок. Они сходятся к **семи системным первопричинам**. Почти каждый пункт из разделов A–G — это симптом одного из этих корней, проявленный в конкретном месте. Исправление корня закрывает целую ветку симптомов; заплатка на симптом оставляет корень живым и порождает следующий.

Ниже каждый корень: **определение** (одно отклонение, а не список), **трассировка** (как из него вырастают конкретные ID по разделам) и **где он живёт**. Это верхнеуровневый разбор; более узкую версию по отдельным границам см. в секции [«Корневые причины»](#корневые-причины) ниже.

### R1. Граница домена не типизирована — ошибка теряет структуру на входе в систему

**Определение.** Реальные адаптеры внешних сервисов возвращают `fmt.Errorf(...)` вместо `*domain.AppError`. HTTP-статус и признак «повторяемо ли» существуют только как **подстрока в тексте ошибки**, а не как поле.

**Трассировка.** Одно отклонение (`billing/http_client.go:206-208` и все прочие адаптеры) расходится вверх по стеку:
- `errors.As(err, &appErr)` в обработчике никогда не срабатывает → **все** ошибки внешних сервисов схлопываются в `500 INTERNAL_ERROR` → **D-02**;
- `402 Insufficient Funds` от Billing доезжает клиентом как `500` → неверный контракт → **C-07**;
- классификация «ретраить или нет» вынужденно делается через `strings.Contains(msg, "status 5")` → **C-07**, и та же строковая логика решает судьбу сообщения в Kafka → **G-05** (устранимый `503` уходит в DLQ как фатальный);
- текст внутренней ошибки утекает клиенту → **E-16**;
- метрики не могут отличить 4xx от 5xx, потому что различия нет уже на уровне типа → **F-15**.

**Где живёт.** Слой `internal/adapters/*/http_client.go`. Корень — отсутствие единого конструктора доменных ошибок с полями `HTTPStatus` и `Retryable`.

### R2. Сборка fail-open, нет единого композиционного корня

**Определение.** При отсутствии переменной окружения слой сборки **молча подставляет mock** вместо отказа старта. Сама сборка при этом продублирована (`api_app`/`worker_app`), поэтому исправление одной ветки не доезжает до второй.

**Трассировка.** Пять независимых мест открываются в полностью незащищённую конфигурацию, и это состояние не видно снаружи:
- `JWT_SECRET`/`AUTH_URL`/`BILLING_URL`/`ADMIN_JWT`/`BILLING_INTERNAL_API_KEY` отсутствуют → mock-аутентификация, mock-биллинг, открытый `/admin`, дефолтные секреты → **E-03, E-04, E-06, E-08, E-17, E-21**;
- ни одно из этих условий не логируется и не отражается в `/health` → сервис выглядит здоровым в открытой конфигурации → усиливается **F-02**;
- дублированная сборка (**D-08**) — причина того, что API поднимает consumer, который никогда не стартует (**F-07**), и механизм, которым несобирающийся вызов доехал до HEAD (**D-01**).

**Где живёт.** `internal/app/api_app.go`, `internal/app/worker_app.go`. Корень — нет единой точки сборки с политикой fail-closed при `APP_ENV=production`.

### R3. Нет связного контракта exactly-once на денежном пути

**Определение.** Идемпотентность и компенсация саги пришиты кусочно, каждый механизм со своим представлением ключа, TTL и владения. Нет единой транзакционной модели «списал → произвёл → зафиксировал» с одним ключом на всём пути.

**Трассировка.** Это самая широкая ветка — она пересекает A, B, C и G:
- ключ идемпотентности не привязан к пользователю → ответ, оплаченный B, отдаётся A → **B-01**;
- не-2xx удаляет маркер уже после списания → повторная оплата → **B-04**;
- bulk не пробрасывает ключ в BarcodeGen, а DLQ хранит батч целиком → реплей оплачивает успешные элементы заново → **B-05, B-10, G-06**;
- `Reserve` ставит маркер на 2 мин, `Set` — на 24 ч; обработка дольше 2 мин → дубль проходит резервацию повторно → **G-02**;
- `Unlock` делает безусловный `DEL` без owner-token → запоздавший unlock снимает чужой лок → **G-01**;
- компенсация (`Release`) выполняется на уже отменённом `ctx` → средства заблокированы навсегда → **A-01**;
- SIGTERM между списанием и коммитом offset → двойное списание → **A-04**;
- сбой `Capture` теряет созданные баркоды, fallback-расчёт расходится со списанным → **C-12, C-13**.

**Где живёт.** `internal/usecase/*_usecase.go` (сага), `internal/adapters/idempotency/*`, `internal/transport/http/gin/idempotency_middleware.go`. Корень — идемпотентность как middleware поверх, а не как свойство одной транзакции.

### R4. Сырые порты в обработчике — бизнес-слой не является обязательным проходом

**Определение.** `APIHandler` держит `ports.BarcodeGenClient`/`ports.HistoryClient`/`ports.BulkConsumer` рядом с usecase, поэтому существует путь к продукту в обход бизнес-правил.

**Трассировка.**
- `pdf417`/`code128` дергают `BarcodeGenClient` напрямую → тот же продукт без quote/block/capture → бесплатная генерация платного → **D-04, D-12**;
- поле `history` в обработчике — единственная причина, по которой возможен IDOR: чтение чужого баркода не проходит через usecase, где живёт проверка владельца → **E-01, E-02**.

**Где живёт.** `internal/transport/http/gin/api_handler.go` (состав структуры). Корень — обработчик зависит от портов адаптеров, а не только от usecase.

---

### R5. Нет ворот верификации и контракта mock↔real

**Определение.** Нет `go build ./...` в проверке, нет CI, а пакет сборки без тестов; параллельно mock-реализации портов написаны руками и не связаны контрактным тестом с real, поэтому расходятся по смыслу при совпадающих сигнатурах.

**Трассировка.**
- `internal/app` — единственный пакет без тестов, `make test` не собирает, CI отсутствует → несобирающийся HEAD доехал незамеченным → **D-01, D-05, F-19, F-20**;
- mock возвращает ошибку без статуса, real — со статусом в тексте → retry-путь неисполним в dev и непокрываем → **D-03**;
- `Stats()` у real деструктивен (snapshot-since-last-call), mock — нет → `PendingCount`/`Stats()` врут → **D-07, F-08, G-10**;
- `UNIT_PRICE` в real — цена, в mock — коэффициент баланса → дефолт даёт `Partial` на любой запрос → **D-15**.

**Где живёт.** `Makefile`, отсутствующий `.github/workflows/`, `internal/adapters/*/mock_client.go`. Корень — контракт порта проверяется компилятором (синтаксис), но не тестом (семантика).

### R6. Полномочия по конфигурации и данным размазаны, без валидации на загрузке

**Определение.** Один и тот же факт (обязательность поля, значение цены, путь к конфигу, набор секретов) задан в нескольких местах, ни одно из которых не назначено единственным источником, и конфиг не валидируется при загрузке.

**Трассировка.** Дефекты живут не в коде, а в промежутке между кодом, `.env.example` и YAML:
- обязательность поля задана в `requiredInputFields`, `schema.fields[].required` и `calculationChain[].dependsOn` одновременно и несогласованно → единственная поставляемая ревизия не генерируется → **C-19**;
- `UNIT_PRICE` (см. R5) → **D-15**;
- дубль каталога `internal/app/configs/` как костыль под относительные пути → **F-17**;
- `JWT_SECRET` есть в коде, но отсутствует в `.env.example` и compose → дефолт неперекрываем штатно → **E-21**.

**Где живёт.** `internal/config/config.go` (нет `Validate()`), `configs/revisions/*.yaml`, `.env.example`, `docker-compose*.yml`. Корень — нет валидации конфигурации при старте и единого источника истины.

---

### R7. Денежный путь не наблюдаем

**Определение.** У саги нет метрик исходов, нет трассировки и нет health, отражающего реальное состояние зависимостей — поэтому отказ на денежном пути происходит молча.

**Трассировка.**
- нет счётчиков исходов саги → провал компенсации (R3 / **A-01**: деньги заблокированы навсегда) не инкрементирует ничего и принципиально не алертится → **F-06**;
- нет `traceID`/`X-Request-Id`/OTel, `CorrelationID` объявлен, но нигде не читается → связать HTTP-запрос → сагу → события Kafka нечем при разборе жалобы «списали, баркод не пришёл» → **F-04**;
- `/health` статичен (`{"status":"ok"}`), не проверяет Redis/Kafka/Billing → открытая или сломанная конфигурация выглядит здоровой → **F-02, F-03**.

**Где живёт.** `internal/transport/http/gin` (health, middleware метрик), отсутствие инструментирования в usecase. Корень — наблюдаемость не встроена в сагу, а добавлена как HTTP-метрики общего вида.

## Метод

Каждая находка проверена в контексте кодовой базы, а не выведена из чтения:

- **Трассировка по коду** — от точки входа через слои до внешнего вызова, с номерами строк.
- **Исполняемые пробы** — временные тесты (`httptest`, стабы портов, `-race`), подтверждающие поведение. Пробы удалены после снятия результата, продакшн-код не изменён.
- **Сверка с исходниками зависимостей** — семантика `kafka-go`, `go-redis`, `gin` проверялась в `GOMODCACHE`, а не по памяти. Так найден D-07/F-08 (деструктивность `Stats()`).
- **`go build` / `go vet` / `go test -race`** — для подтверждения дрейфа сигнатур и гонок.

Три гипотезы проверены и **опровергнуты** — оставлены в отчёте с доказательствами, чтобы их не проверяли повторно: E-18 (path traversal), E-19 (SSRF), E-20 (JWT alg confusion), плюс F-21 (взрыв кардинальности метрик).

Рабочее дерево не изменялось: правки не вносились, только отчёты в `docs/audit/`.

## Fail-open как класс

Пять независимых мест открываются при отсутствии переменной окружения:

| ID | Отсутствует ENV | Результат |
|---|---|---|
| E-03 + **E-21** | `JWT_SECRET` | Дефолтный секрет; переменной нет в `.env.example` и compose, поэтому в prod-like режиме дефолт применяется **даже при корректно заполненном `.env`** |
| E-04 | `AUTH_URL` | Mock-аутентификация принимает любой токен |
| E-06 | `BILLING_URL` | Mock-биллинг, генерация бесплатна |
| E-08 | `ADMIN_JWT` / `INTERNAL_SERVICE_JWT` | Пустой ожидаемый токен открывает `/admin` и `/internal` |
| E-17 | `BILLING_INTERNAL_API_KEY` | Дефолт `dev-billing-key` |

Ни одно из этих условий не логируется как предупреждение и не отражается в `/health` (F-02) — сервис выглядит здоровым в полностью открытой конфигурации. Общее исправление: fail-closed при `APP_ENV=production` — отказ старта вместо подстановки mock.

## Дрейф конфигурации и данных

Четыре дефекта существуют не в коде, а в промежутке между кодом, `.env.example` и YAML-конфигами. Изолированное чтение любого одного файла их не выявляет, тесты не покрывают.

| ID | Дефект | Почему не виден в коде |
|---|---|---|
| E-21 | `JWT_SECRET` отсутствует в `.env.example` и compose | В коде объявлен и документирован; не доходит до процесса в prod-like режиме |
| D-15 | `UNIT_PRICE` — цена в real, коэффициент в mock | Типы совпадают (`float64`), mock честно док��ментирует свою семантику |
| C-19 | Поставляемая ревизия не генерируется с документированным минимумом | Дефект в YAML; тесты цепочки используют inline-конфиги, не поставляемый файл |
| F-17 | Дубль `internal/app/configs/` под относительные пути | Оба каталога существуют и читаются |

Практическое следствие D-15: при дефолтном `UNIT_PRICE=0.50` mock-биллинг отдаёт `Partial=true` **на любой** `units`, а при `units=1` — отказ. Значит разработчик, поднявший сервис по README, видит исключительно partial-путь и никогда не наблюдает нормальный полный флоу — тот, который содержит C-11, C-15 и B-03. Одновременно C-19 означает, что и partial-путь недостижим для единственной ревизии: запрос падает на цепочке раньше биллинга.

Совместно это даёт нерабочий сценарий «первого запуска»: следуя документации, получить успешную генерацию нельзя.

## Корневые причины

Три дефекта границ являются причинами дефектов, зафиксированных в других разделах как отдельные проблемы. Исправление корня снимает необходимость в частных заплатках.

**D-02 — реальные адаптеры никогда не возвращают `*domain.AppError`.**
Все ошибки внешних сервисов — `fmt.Errorf`, поэтому `errors.As` в обработчике не срабатывает и всё схлопывается в `500 INTERNAL_ERROR`.
→ снимает **C-07** (классификация ретраев через `strings.Contains(msg, "status 5")` существует только потому, что структурной ошибки нет), **E-16** (тело внешнего ��ервиса утекает клиенту), улучшает **F-15** (метрики не различают 4xx и 5xx).

**D-04 + D-12 — сырые порты в HTTP-обработчике.**
`APIHandler` держит `ports.BarcodeGenClient`, `ports.HistoryClient`, `ports.BulkConsumer` наряду с usecase, что структурно разрешает обход бизнес-логики.
→ снимает обход биллинга и делает **E-01/E-02** (IDOR) невозможными структурно: чтение через usecase несёт проверку владельца там же, где она уже есть для edit.

**D-08 — дублированная сборка `api_app`/`worker_app`.**
→ снимает **F-07** (API создаёт consumer, который никогда не стартует) и часть **A-04** (конкуренция за один `group.id`), а также механизм доставки **D-01**.

## Порядок исправления

| Шаг | Пункты | Обоснование |
|---|---|---|
| 1 | **D-01/F-01** | Зелёная сборка — предпосылка проверки всего остального |
| 2 | **D-05**, **F-19**, **F-20** | `var _ ports.X = ...`, `go build ./...` в `make check`, CI. Предотвращает повторение шага 1 |
| 3 | **E-03, E-04, E-06, E-08, E-17, E-21** | Fail-closed в production + проброс секретов в compose. Самая высокая отдача на единицу правки |
| 4 | **E-01, E-02** + **D-04, D-12** | Проверка владельца и удаление сырых портов — одной правкой |
| 5 | **A-01, A-02, A-06** | Компенсация на `context.WithoutCancel`, продление лока, graceful drain |
| 6 | **D-02, D-03** + **C-07** | Типизированные ошибки адаптеров с признаком `Retryable` |
| 7 | **B-01, B-02, B-04** | Ключ идемпотентности: скоуп по пользователю, хеш тела, корректный TTL |
| 8 | **F-02, F-03, F-06, F-04** | Health с проверкой зависимостей, метрики саги, трассировка |

## Ограничения аудита

- **Только BFF.** Поведение Billing, BarcodeGen, AI, History, Auth не проверялось — выводы об их контрактах сделаны по коду адаптеров BFF. E-19 (SSRF) закрыт в BFF, но может присутствовать в BarcodeGen, который реально загружает `signatureUrl`.
- **Статический анализ и локальные пробы.** Интеграционного прогона против живых сервисов не выполнялось: HEAD не собирается (D-01).
- **Нагрузочные характеристики не измерялись.** Оценки бюджета времени в A-01 и A-03 — расчётные, по константам таймаутов и backoff в коде.
- **Многореплика не воспроизводилась.** A-05 (in-memory лок и store) выведен из кода, а не из наблюдения при >1 реплике.
- **Отчёты не содержат правок.** Все предложенные багфиксы — рекомендации; в кодовую базу изменения не вносились.
