## Метод

Каждая находка проверена в контексте кодовой базы, а не выведена из чтения:

- **Трассировка по коду** — от точки входа через слои до внешнего вызова, с номерами строк.
- **Исполняемые пробы** — временные тесты (`httptest`, стабы портов, `-race`), подтверждающие поведение. Пробы удалены после снятия результата, продакшн-код не изменён.
- **Сверка с исходниками зависимостей** — семантика `kafka-go`, `go-redis`, `gin` проверялась в `GOMODCACHE`, а не по памяти. Так найден D-07/F-08 (деструктивность `Stats()`).
- **`go build` / `go vet` / `go test -race`** — для подтверждения дрейфа сигнатур и гонок.

Три гипотезы проверены и **опровергнуты** — оставлены в отчёте с доказательствами, чтобы их не проверяли повторно: E-18 (path traversal), E-19 (SSRF), E-20 (JWT alg confusion), плюс F-21 (взрыв кардинальности метрик).

Рабочее дерево не изменялось: правки не вносились, только отчёты в `docs/audit/`.

## Блокирующее

**D-01 / F-01 — HEAD не компилируется.**

```
$ go build ./...
internal/app/api_app.go:219:48: not enough arguments in call to kafkaadapter.NewConsumer
	have ([]string, string, *kafkatransport.BulkJobHandler)
	want ([]string, string, kafkaadapter.MessageHandler, kafkaadapter.DLQProducer)
```

Падают `cmd/api`, `cmd/worker`, `internal/app`. Коммит «Kafka DLQ» добавил четвёртый параметр и обновил одну точку вызова из двух.

Это первый пункт на исправление: пока сборка красная, ни одно другое исправление нельзя ни собрать, ни проверить. Дефект доехал до HEAD потому, что `internal/app` — единственный пакет без тестов (D-05), `make test` не вызывает `go build ./...` (F-19), а CI отсутствует (F-20).

## Денежные дефекты

Проект списывает деньги пользователей, поэтому эти пункты выделены отдельно.

| ID | Дефект | Последствие |
|---|---|---|
| A-01 | `Release` на отменённом контексте | Средства заблокированы навсегда, компенсация не выполняется |
| A-04 | SIGTERM между списанием и коммитом offset | Двойное списание |
| B-01 | Ключ идемпотентности не привязан к пользователю | Пользователь A получает ответ, оплаченный пользователем B |
| B-04 | Не-2xx удаляет маркер после списания | Повторная оплата того же запроса |
| B-05 | Bulk не передаёт ключ в BarcodeGen | Реплей оплачивает заново |
| B-10 | DLQ хранит батч целиком | Реплей оплачивает успешные элементы повторно |
| C-12 | Сбой `Capture` теряет созданные баркоды | Пользователь не получает оплаченное |
| C-13 | Fallback-расчёт расходится с списанным | Списано больше, чем показано |
| D-04 | `pdf417`/`code128` минуют биллинг | Бесплатная генерация платного продукта |
| E-06 | Без `BILLING_URL` поднимается mock | Полностью бесплатная генерация |

Единый источник большинства из них — отсутствие метрик исходов саги (F-06): провал компенсации не инкрементирует ничего и принципиально не алертится.

## Fail-open как класс

Пять независимых мест открываются при отсутствии переменной окружения:

| ID | Отсутствует ENV | Результат |
|---|---|---|
| E-03 + **E-21** | `JWT_SECRET` | Дефолтный секрет; переменной нет в `.env.example` и compose, поэтому в prod-like режиме дефолт применяется **даже при корректно заполненном `.env`** |
| E-04 | `AUTH_URL` | Mock-аутентификация принимает любой токен |
| E-06 | `BILLING_URL` | Mock-биллинг, генерация бесплатна |
| E-08 | `ADMIN_JWT` / `INTERNAL_SERVICE_JWT` | Пустой ожидаемый токен открывает `/admin` и `/internal` |
| E-17 | `BILLING_INTERNAL_API_KEY` | Дефолт `dev-billing-key` |

Ни одно из этих условий не логируется как предупреждение и не отражается в `/health` (F-02) — сервис выглядит здоровым в полностью открытой конфигурации. Общее исправление: fail-closed при `APP_ENV=production` — отказ старта вместо подстановки mock.

## Дрейф конфигурации и данных

Четыре дефекта существуют не в коде, а в промежутке между кодом, `.env.example` и YAML-конфигами. Изолированное чтение любого одного файла их не выявляет, тесты не покрывают.

| ID | Дефект | Почему не виден в коде |
|---|---|---|
| E-21 | `JWT_SECRET` отсутствует в `.env.example` и compose | В коде объявлен и документирован; не доходит до процесса в prod-like режиме |
| D-15 | `UNIT_PRICE` — цена в real, коэффициент в mock | Типы совпадают (`float64`), mock честно документирует свою семантику |
| C-19 | Поставляемая ревизия не генерируется с документированным минимумом | Дефект в YAML; тесты цепочки используют inline-конфиги, не поставляемый файл |
| F-17 | Дубль `internal/app/configs/` под относительные пути | Оба каталога существуют и читаются |

Практическое следствие D-15: при дефолтном `UNIT_PRICE=0.50` mock-биллинг отдаёт `Partial=true` **на любой** `units`, а при `units=1` — отказ. Значит разработчик, поднявший сервис по README, видит исключительно partial-путь и никогда не наблюдает нормальный полный флоу — тот, который содержит C-11, C-15 и B-03. Одновременно C-19 означает, что и partial-путь недостижим для единственной ревизии: запрос падает на цепочке раньше биллинга.

Совместно это даёт нерабочий сценарий «первого запуска»: следуя документации, получить успешную генерацию нельзя.

## Корневые причины

Три дефекта границ являются причинами дефектов, зафиксированных в других разделах как отдельные проблемы. Исправление корня снимает необходимость в частных заплатках.

**D-02 — реальные адаптеры никогда не возвращают `*domain.AppError`.**
Все ошибки внешних сервисов — `fmt.Errorf`, поэтому `errors.As` в обработчике не срабатывает и всё схлопывается в `500 INTERNAL_ERROR`.
→ снимает **C-07** (классификация ретраев через `strings.Contains(msg, "status 5")` существует только потому, что структурной ошибки нет), **E-16** (тело внешнего ��ервиса утекает клиенту), улучшает **F-15** (метрики не различают 4xx и 5xx).

**D-04 + D-12 — сырые порты в HTTP-обработчике.**
`APIHandler` держит `ports.BarcodeGenClient`, `ports.HistoryClient`, `ports.BulkConsumer` наряду с usecase, что структурно разрешает обход бизнес-логики.
→ снимает обход биллинга и делает **E-01/E-02** (IDOR) невозможными структурно: чтение через usecase несёт проверку владельца там же, где она уже есть для edit.

**D-08 — дублированная сборка `api_app`/`worker_app`.**
→ снимает **F-07** (API создаёт consumer, который никогда не стартует) и часть **A-04** (конкуренция за один `group.id`), а также механизм доставки **D-01**.

## Порядок исправления

| Шаг | Пункты | Обоснование |
|---|---|---|
| 1 | **D-01/F-01** | Зелёная сборка — предпосылка проверки всего остального |
| 2 | **D-05**, **F-19**, **F-20** | `var _ ports.X = ...`, `go build ./...` в `make check`, CI. Предотвращает повторение шага 1 |
| 3 | **E-03, E-04, E-06, E-08, E-17, E-21** | Fail-closed в production + проброс секретов в compose. Самая высокая отдача на единицу правки |
| 4 | **E-01, E-02** + **D-04, D-12** | Проверка владельца и удаление сырых портов — одной правкой |
| 5 | **A-01, A-02, A-06** | Компенсация на `context.WithoutCancel`, продление лока, graceful drain |
| 6 | **D-02, D-03** + **C-07** | Типизированные ошибки адаптеров с признаком `Retryable` |
| 7 | **B-01, B-02, B-04** | Ключ идемпотентности: скоуп по пользователю, хеш тела, корректный TTL |
| 8 | **F-02, F-03, F-06, F-04** | Health с проверкой зависимостей, метрики саги, трассировка |
| 9 | **A-05** + **F-05, F-12** | Готовность к >1 реплике; метрики и healthcheck воркера |
| 10 | **C-19, D-15** | Дрейф конфигурации: согласовать YAML ревизии и mock-биллинг, иначе сценарий «первого запуска» остаётся нерабочим |

Шаги 1-2 не меняют поведения, но без них остальные девять невозможно верифицировать.

## Ограничения аудита

- **Только BFF.** Поведение Billing, BarcodeGen, AI, History, Auth не проверялось — выводы об их контрактах сделаны по коду адаптеров BFF. E-19 (SSRF) закрыт в BFF, но может присутствовать в BarcodeGen, который реально загружает `signatureUrl`.
- **Статический анализ и локальные пробы.** Интеграционного прогона против живых сервисов не выполнялось: HEAD не собирается (D-01).
- **Нагрузочные характеристики не измерялись.** Оценки бюджета времени в A-01 и A-03 — расчётные, по константам таймаутов и backoff в коде.
- **Многореплика не воспроизводилась.** A-05 (in-memory лок и store) выведен из кода, а не из наблюдения при >1 реплике.
- **Отчёты не содержат правок.** Все предложенные багфиксы — рекомендации; в кодовую базу изменения не вносились.
