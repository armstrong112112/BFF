## G-01. `RedisEditLocker.Unlock` — безусловный `DEL`, снимающий чужой лок

**Суть.** `Unlock` выполняет `DEL edit-lock:{barcodeID}` без проверки, что удаляемый лок принадлежит именно этому вызывающему. После истечения TTL (30 с) лок может перейти к другому запросу; запоздавший `Unlock` первого запроса удалит лок второго, открыв окно для третьего. Это классический баг «удаление чужого лока», ровно тот, против которого существует паттерн Redlock с owner-token.

**Место.** `internal/adapters/idempotency/redis_locker.go:52-57` (`Unlock`), `:38-47` (`TryLock`), `internal/usecase/edit_usecase.go:79` (`defer Unlock`).

**Подробное описание.**

`TryLock` пишет фиксированное значение `"1"`, не уникальный токен:

```go
res, err := l.client.SetArgs(ctx, editLockPrefix+barcodeID, "1", redis.SetArgs{
    Mode: "NX", TTL: editLockTTL, // 30s
}).Result()
```

`Unlock` удаляет безусловно:

```go
func (l *RedisEditLocker) Unlock(ctx context.Context, barcodeID string) error {
    if err := l.client.Del(ctx, editLockPrefix+barcodeID).Err(); err != nil { ... }
}
```

Проба на `MemoryEditLocker` (владения нет в обеих реализациях):

```
PROBE GR-01 CONFIRMED: Unlock без owner-token удалил чужой лок -> C захватил лок, пока B его держит
--- PASS
```

Сценарий на реальном Redis:

1. Запрос **A** захватывает `edit-lock:barcode-1`, TTL 30 с. Начинает `Block → GeneratePDF417 → PublishBarcodeEdited`.
2. BarcodeGen тормозит, A выполняется дольше 30 с. Redis снимает лок по TTL.
3. Запрос **B** (тот же `barcodeID`, другой `X-Idempotency-Key`) захватывает освободившийся лок и начинает своё редактирование.
4. A наконец завершает работу, срабатывает `defer Unlock(ctx, barcodeID)` → `DEL edit-lock:barcode-1` → **удаляется лок B**.
5. Запрос **C** захватывает лок, пока B ещё внутри критической секции.

Итог — то самое, против чего лок и ставился (комментарий `edit_usecase.go:63-64`): злоумышленник с параллельными запросами и разными идемпотентными ключами использует бесплатное редактирование более одного раза. G-01 сводит на нет защиту A-раздела по free-edit: лок есть, но не держит под нагрузкой, а именно под нагрузкой атака и осмысленна.

**Предлагаемый багфикс.** Owner-token + атомарное освобождение через Lua (compare-and-delete):

```go
func (l *RedisEditLocker) TryLock(ctx context.Context, barcodeID string) (string, bool, error) {
    token := uuid.NewString()
    res, err := l.client.SetArgs(ctx, editLockPrefix+barcodeID, token, redis.SetArgs{
        Mode: "NX", TTL: editLockTTL,
    }).Result()
    if err != nil && err != redis.Nil {
        return "", false, fmt.Errorf("edit locker: try lock %q: %w", barcodeID, err)
    }
    return token, res == "OK", nil
}

var unlockScript = redis.NewScript(`
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end`)

func (l *RedisEditLocker) Unlock(ctx context.Context, barcodeID, token string) error {
    return unlockScript.Run(ctx, l.client, []string{editLockPrefix + barcodeID}, token).Err()
}
```

Порт `EditLocker` меняется: `TryLock` возвращает токен, `Unlock` его принимает. В `edit_usecase.go`:

```go
token, acquired, lockErr := u.locker.TryLock(ctx, barcodeID)
...
defer func() { _ = u.locker.Unlock(context.WithoutCancel(ctx), barcodeID, token) }()
```

Дополнительно: если критическая секция может легитимно превышать 30 с, добавить watchdog-продление TTL (`PEXPIRE` по таймеру), пока операция идёт.

**Комментарий.** Это не гипотетика: комментарий в `edit_usecase.go` прямо декларирует лок как anti-race-меру против повторного использования free-edit, то есть корректность G-01 напрямую влияет на денежный инвариант. Связано с A-разделом (гонки free-edit) и с G-07 (ctx у Unlock): даже после добавления owner-token отмена запроса не должна мешать освобождению.

## G-02. Расхождение TTL: `Reserve` = 2 мин, обработка bulk может длиться дольше

> **⇔ Дубль. Канонично: [A-03](A-concurrency-races.md). В итоговом счёте учитывается один раз под A-03.** Тот же дефект (`redis_store.go:18` `shortTTL` против `s.ttl` в `Set`), угол раздела G — bulk/DLQ-контекст и связка с D-15. Уникальный вклад этой записи — heartbeat-фикс через `Refresh`/`PEXPIRE`; независимым дефектом не считается.

**Суть.** `Reserve` ставит маркер с `shortTTL = 2*time.Minute`, а `Set` перезаписывает его полным `s.ttl` (24 ч) только после успешного завершения. Если обработка между Reserve и Set длится дольше 2 минут, in-flight маркер истекает; параллельный дубликат с тем же ключом проходит `Reserve` заново и выполняет сайд-эффект второй раз. Для write-операций (generate/edit) это двойное списание/двойная генерация под одним идемпотентным ключом.

**Место.** `internal/adapters/idempotency/redis_store.go:18` (`shortTTL`), `:72-83` (`Reserve`), `:87-92` (`Set`), `internal/transport/http/gin/idempotency_middleware.go:85,122`.

**Подробное описание.**

Комментарий `redis_store.go:15-18` объясняет замысел shortTTL: при крэше Pod'а маркер снимается через 2 минуты, а не блокирует клиента на сутки (Zombie Lock fix). Замысел верный, но выбранное значение создаёт новый инвариант: **обработка обязана уложиться в shortTTL**, иначе идемпотентность ломается. Этот инвариант нигде не проверяется и не защищён.

Порядок в middleware:

1. `:85` `Reserve` → `SET NX EX 120s`.
2. `c.Next()` — синхронная обработка. Для generate это `Quote → Block → GeneratePDF417 → Capture → PublishBarcodeGenerated`; для bulk-элементов путь ещё длиннее.
3. `:122` `Set` → `SET EX 24h` (перезапись маркера готовым ответом).

Если шаг 2 длится > 120 с (медленный BarcodeGen, деградация Billing, крупный batch), к моменту прихода дубля на шаге 1 маркер уже истёк. Дубль резервирует ключ заново и повторяет шаг 2. Оба запроса дойдут до `Block`/`Capture` — двойное списание. Ровно тот класс, который B-раздел закрывает для быстрых операций, но shortTTL открывает для медленных.

Почему это критичнее, чем кажется: связка с D-15. В mock-режиме (дефолтный `UNIT_PRICE=0.50`) каждый запрос идёт по partial-пути, а с реальным медленным BarcodeGen превышение 2 минут на крупном заказе — штатная ситуация, не крайний случай.

**Предлагаемый багфикс.** Развязать «anti-zombie TTL» и «длительность обработки». Вариант — heartbeat-продление маркера, пока обработка идёт:

```go
// В middleware после Reserve запустить продление:
stop := make(chan struct{})
go func() {
    t := time.NewTicker(shortTTL / 2)
    defer t.Stop()
    for {
        select {
        case <-stop:
            return
        case <-t.C:
            _ = store.Refresh(c.Request.Context(), key, shortTTL) // PEXPIRE
        }
    }
}()
c.Next()
close(stop)
```

с новым методом `Refresh(ctx, key, ttl)` → `PEXPIRE`. Тогда маркер жив, пока жив обработчик, и истекает через 2 минуты только при реальном крэше (heartbeat остановился). Альтернатива проще, но грубее: поднять shortTTL до максимально допустимой длительности обработки (например, `maxRequestTimeout + запас`) — но тогда частично возвращается zombie-lock на эту длительность.

**Комментарий.** Найдено чтением, `TestProbeGR02` заскипался из-за некорректного числового сравнения `Duration` в самой пробе (моя ошибка в пробе, не в коде) — расхождение TTL подтверждено трассировкой: `Reserve` жёстко использует `shortTTL`, `Set` — `s.ttl`, между ними произвольно долгий `c.Next()`. Прямо связано с B-разделом (exactly-once) и с G-01 (edit-lock TTL 30 с имеет ту же болезнь для edit-пути).

## G-03. API-side consumer собран без DLQ

**Суть.** `NewConsumer` принимает 4-й аргумент `dlq Publisher`, и `worker_app.go:133` его передаёт, а `api_app.go:219` — **нет** (3 аргумента). То есть на API-стороне DLQ-публикатор `nil`, и `publishDLQ` немедленно возвращается, ничего не публикуя. Плюс это тот самый вызов, который не компилируется (D-01/F-01): сигнатура 4-арг, вызов 3-арг.

**Место.** `internal/app/api_app.go:219` (3 арг, не компилируется), `internal/app/worker_app.go:133` (4 арг, корректно), `internal/adapters/kafka/consumer.go:30,86-90`.

**Подробное описание.**

```go
// worker_app.go:133 — правильно
consumer = kafkaadapter.NewConsumer(cfg.Kafka.Brokers, cfg.Kafka.GroupID, handler.Handle, kafkaProducer)

// api_app.go:219 — 3 аргумента, DLQ отсутствует (и код не собирается)
bulkConsumer = kafkaadapter.NewConsumer(cfg.Kafka.Brokers, cfg.Kafka.GroupID, bulkHandler.Handle)
```

`publishDLQ` при `nil`-публикаторе — no-op:

```go
func (c *Consumer) publishDLQ(...) {
    if c.dlqPublisher == nil {
        return
    }
    ...
}
```

Два следствия. Первое — блокирующее: HEAD не собирается (см. D-01/F-01), поэтому API-consumer вообще не запускается. Второе — архитектурное: даже после починки сигнатуры, если её «починить» добавлением `nil`, API-путь потеряет сообщения при ошибке молча. Правильная починка — передать `kafkaProducer` как в worker.

Важно и то, что в `api_app.go` bulk-consumer **всё равно не стартует** (`APIApp.Run` не вызывает `Start()` — см. F-07), поэтому на практике DLQ-путь на API-стороне неактив��н целиком: сначала не собирается, а если собрать — не запускается. Это делает `bulk/wake` на API-стороне полностью декоративным.

**Предлаг��емый багфикс.** Привести вызов к 4-арг и передать реальный публикатор:

```go
// api_app.go:219
bulkConsumer = kafkaadapter.NewConsumer(cfg.Kafka.Brokers, cfg.Kafka.GroupID, bulkHandler.Handle, kafkaProducer)
```

и запускать его в `APIApp.Run` (или убрать bulk-consumer из API вовсе, оставив только в worker — если по архитектуре bulk обрабатывает только worker). Выбор зависит от намерения: два разных groupID на один топик означают, что и API, и worker будут конкурировать за партиции. Скорее всего bulk-consumer в API — ошибка копирования из worker_app, и его следует удалить, а не чинить.

**Комментарий.** Это пересечение трёх разделов: D-01 (контракт конструктора), F-01 (сборка), F-07 (Start не вызывается). Здесь фиксирую именно DLQ-аспект: даже приведя к компилируемому виду наугад (`nil`), легко получить тихую потерю сообщений. Первопричина — дублированный wiring `api_app`/`worker_app` (D-09) разошёлся при добавлении DLQ.

## G-04. DLQ теряет сообщение при падении публикации

**Суть.** `publishDLQ` при ошибке публикации в DLQ только логирует, после чего `Start` всё равно коммитит offset. Если брокер недоступен ровно в момент DLQ-публикации (а он часто недоступен именно тогда, когда сообщения начинают падать), сообщение теряется безвозвратно: из основного топика вычитано и закоммичено, в DLQ не попало.

**Место.** `internal/adapters/kafka/consumer.go:69-78` (unmarshal-путь), `:71-73` (handler-путь), `:100-106` (publishDLQ), `:75` (`CommitMessages` после DLQ).

**Подробное описание.**

```go
if err := c.handler(ctx, msg); err != nil {
    log.Printf(...)
    c.publishDLQ(ctx, m, "handler", err) // ошибка внутри проглатывается
}
// Коммитим offset независимо от результата publishDLQ
if err := c.reader.CommitMessages(ctx, m); err != nil { log.Printf(...) }
```

`publishDLQ` при неудаче:

```go
if err := c.dlqPublisher.Publish(ctx, TopicBulkTasksDLQ, rec); err != nil {
    log.Printf("DLQ publish error: ...") // и всё
}
```

Комментарий автора (`:98-99`) честно фиксирует замысел «не блокировать основной поток». Но цена — потеря данных: after commit сообщение недостижимо ни в основном топике, ни в DLQ. Для bulk-задач (десятки-сотни документов в сообщении) это потеря целого оплаченного заказа без следа.

**Предлагаемый багфикс.** Не коммитить offset, если DLQ-публикация не удалась — тогда сообщение перечитается и попадёт в DLQ на следующей попытке:

```go
dlqOK := true
if err := c.handler(ctx, msg); err != nil {
    log.Printf(...)
    dlqOK = c.publishDLQ(ctx, m, "handler", err) // возвращает bool
}
if !dlqOK {
    // не коммитим: перечитаем и попробуем в DLQ снова (с backoff)
    time.Sleep(dlqRetryBackoff)
    continue
}
if err := c.reader.CommitMessages(ctx, m); err != nil { ... }
```

`publishDLQ` вернуть `bool` (успех). Для unmarshal-пути (невалидный JSON) сообщение не станет валиднее при перечитывании, но и оно не должно теряться — здесь оправдан отдельный persistent fallback (например, лог в файл/БД), поскольку бесконечный replay невалидного JSON заблокирует партицию. Компромисс: ограниченное число ретраев DLQ, затем commit с алертом.

**Комментарий.** Связано с B-разделом (гарантии доставки) и G-11 (нет алерта на DLQ). Формулировка «не блокировать основной поток» верна как цель, но реализована как «терять при сбое» — правильный компромисс это backpressure (притормозить), а не потеря.

## G-05. `handler`-ошибка → DLQ и commit одновременно: устранимые ошибки становятся фатальными

**Суть.** Любая ошибка хендлера трактуется как «в DLQ и коммит». Различия между устранимой ошибкой (Billing временно недоступен, таймаут) и неустранимой (битые данные) нет. Временный сбой отправляет полностью валидное сообщение в DLQ и коммитит offset — at-least-once вырождается в at-most-once: сообщение не будет переобработано автоматически, хотя достаточно было ретрая.

**Место.** `internal/adapters/kafka/consumer.go:71-79`.

**Подробное описание.**

`handler` возвращает единый `error` без классификации. Один и тот же путь для:

- «BarcodeGen вернул 503» — устранимо, нужен ретрай;
- «в сообщении отсутствует обязательное поле» — неустранимо, нужен DLQ.

Обе ситуации → DLQ + commit. При деградации внешнего сервиса на минуту весь трафик за эту минуту осядет в DLQ и потребует ручного replay, хотя сервис сам восстановился бы. Это зеркало C-07 (классификация ошибок по подстроке) и D-02 (адаптеры возвращают безкодовые ошибки): на уровне consumer тоже нет способа отличить retryable от terminal, потому что ошибки бесструктурны.

**Предлагаемый багфикс.** Ввести типизацию ошибок хендлера и различать пути:

```go
err := c.handler(ctx, msg)
switch {
case err == nil:
    // commit
case errors.Is(err, domain.ErrRetryable):
    // не коммитим, backoff, перечитаем (с ограничением попыток -> потом DLQ)
default: // terminal
    c.publishDLQ(...); // commit
}
```

Хендлер должен возвращать `domain.ErrRetryable` для сетевых/5xx/таймаут-ошибок внешних сервисов. Это требует наличия кодов ошибок в адаптерах (см. фикс D-02) — без него классификация снова сведётся к разбору строк.

**Комментарий.** Зависит от фикса D-02 (структурные ошибки адаптеров). Пока адаптеры возвращают `fmt.Errorf`, корректная классификация на consumer невозможна — это подчёркивает, что D-02 корневой.

## G-06. Нет replay-воркера и дедупа п��и replay → двойной сайд-эффект

**Суть.** `DLQRecord` хранит `RawValue` для проигрывания «1-в-1» (комментарий `dlq.go:5-7`), но воркера/эндпоинта replay в кодовой базе нет, а главное — при любом replay не гарантируется идемпотентность: если исходное сообщение частично обработалось до ошибки (часть документов заказа успела списать деньги и сгенерироваться), повторное проигрывание повторит успешную часть.

**Место.** `internal/adapters/kafka/dlq.go` (только структура), отсутствует replay-обработчик; связь с идемпотентностью bulk-элементов.

**Подробное описание.**

Комментарий обещает replay через akhq/kafkacat/replay-воркер. Но:

1. Replay-воркера нет — значит replay ручной (kafkacat перекладывает `rawValue` обратно в `bulk.tasks`).
2. Идемпотентность bulk устроена на уровне HTTP-middleware (`X-Idempotency-Key`), а сообщения Kafka идут **мимо** этого middleware. Ключа идемпотентности на уровне отдельного bulk-элемента, насколько видно, нет (см. B-раздел про per-item идемпотентность).
3. Значит повторное проигрывание сообщения, у которого 3 из 10 документов успели пройти `Capture`, при replay спишет за эти 3 повторно.

Итог: механизм DLQ спроектирован под replay, но система не готова к безопасному replay. «Переиграть 1-в-1» безопасно только для сообщений, упавших **до** первого сайд-эффекта (unmarshal, ранняя валидация). Для упавших **в середине** replay = двойное списание.

**Предлагаемый багфикс.** Два уровня:

1. Идемпотентность на уровне bulk-элемента: каждый item получает стабильный `itemKey` (например, `batchId:itemIndex`), обработчик проверяет/резервирует его в том же `IdempotencyStore` перед сайд-эффектом. Тогда replay всего сообщения пропустит уже обработанные элементы.
2. Реальный replay-воркер, читающий `bulk.tasks.dlq`, применяющий политику (retry N раз для `errorReason=handler`, ручное решение для `unmarshal`) и публикующий обратно с сохранением `itemKey`.

**Комментарий.** Это самый концептуальный пункт раздела: DLQ есть, replay задекларирован, но безопасного replay нет. Прямо продолжает B-раздел (exactly-once): без per-item ключа exactly-once недостижим ни при обычной обработке, ни при replay.

## G-07. `Unlock`/`Delete` используют request-`ctx`: при отмене клиента ресурс не освобождается

**Суть.** Освобождающие операции (`EditLocker.Unlock` в `defer`, `IdempotencyStore.Delete` в middleware) выполняются с request-контекстом. Если клиент разорвал соединение (таймаут, отмена), `ctx` уже отменён, и `DEL` в Redis не выполнится — лок/маркер остаётся до истечения TTL. Для edit-lock это 30 с блокировки barcode; для idempotency-маркера — до 2 минут 409-ответов на легитимные ретраи.

**Место.** `internal/usecase/edit_usecase.go:79` (`defer Unlock(ctx, ...)`), `internal/transport/http/gin/idempotency_middleware.go:124` (`Delete(c.Request.Context(), key)`).

**Подробное описание.**

```go
// edit_usecase.go:79
defer func() { _ = u.locker.Unlock(ctx, barcodeID) }()
```

`ctx` здесь — производный от request-контекста. При отмене запроса (клиент ушёл) `redis.Del(ctx, ...)` вернёт `context.Canceled`, ничего не удалив. Лок повиснет на TTL. То же в middleware: `store.Delete(c.Request.Context(), key)` на ветке ошибки — если запрос отменён, маркер не снимется, и комментарий middleware («клиент может повторить немедленно») перестаёт выполняться.

Это не смертельно (TTL спасёт), но сводит на нет цель обоих `Delete`/`Unlock` — быстрое освобождение. И усугубляет G-01 (лок держится полный TTL → окно кражи гарантированно открывается) и G-02 (маркер живёт полные 2 минуты → окно повторной резервации).

**Предлагаемый багфикс.** Для освобождающих операций использовать контекст, не связанный с отменой запроса:

```go
defer func() {
    ctxRel, cancel := context.WithTimeout(context.WithoutCancel(ctx), 3*time.Second)
    defer cancel()
    _ = u.locker.Unlock(ctxRel, barcodeID)
}()
```

Аналогично в middleware для `Delete`. `context.WithoutCancel` (Go 1.21+) отвязывает от отмены, но сохраняет values; `WithTimeout` не даёт зависнуть навсегда.

**Комментарий.** Тонкий, но системный: cleanup нельзя вешать на контекст, чья отмена и есть причина cleanup. Связан с G-01 и G-02 — без этого фикса их окна открываются чаще.

## G-08. Три независимых Redis-клиента, без PING при старте, health не проверяет Redis

**Суть.** `NewRedisStore` и `NewRedisEditLocker` создают по своему `redis.NewClient` из одного и того же URL; третий клиент — если Redis используется ещё где-то. Пул соединений не переиспользуется. Ни один конструктор не делает `PING` — некорректный `REDIS_URL` или недоступный Redis обнаружится только на первом запросе. Health-эндпоинт (F-02) Redis не проверяет.

**Место.** `internal/adapters/idempotency/redis_store.go:44-51`, `internal/adapters/idempotency/redis_locker.go:28-33`, `internal/app/api_app.go:70,90`.

**Подробное описание.**

```go
// redis_store.go
return &RedisStore{client: redis.NewClient(opts), ttl: ttl}, nil
// redis_locker.go
return &RedisEditLocker{client: redis.NewClient(opts)}, nil
```

Два клиента на один Redis — два независимых пула соединений, вдвое больше коннектов к серверу без причины (идемпотентность и edit-lock могли бы делить пул). `go-redis` клиент потокобезопасен и предназначен для шаринга.

Отс��тствие `PING`: конструктор возвращает `nil` ошибку даже при полностью недоступном Redis (`ParseURL` проверяет только синтаксис URL). Сервис стартует «здоровым», `/health` отвечает 200 (F-02), а первый же write-запрос падает на `Reserve`. В связке с G-09 это значит: недоступный Redis → все write-запросы получают 409 REQUEST_IN_FLIGHT, что выглядит как «всё дублируется», а не «Redis лежит».

**Предлагаемый багфикс.**

1. Один общий клиент:

```go
func NewRedisClient(url string) (*redis.Client, error) {
    opts, err := redis.ParseURL(url)
    if err != nil { return nil, err }
    c := redis.NewClient(opts)
    ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
    defer cancel()
    if err := c.Ping(ctx).Err(); err != nil {
        return nil, fmt.Errorf("redis ping: %w", err)
    }
    return c, nil
}
```

и передавать этот `*redis.Client` и в `RedisStore`, и в `RedisEditLocker`.

2. Добавить Redis в readiness-проверку `/health` (см. фикс F-02/F-03): `PING` с коротким таймаутом.

**Комментарий.** Связано с F-02/F-03 (health не проверяет зависимости) и G-09. Не критично по данным, но напрямую бьёт по времени обнаружения инцидента: сейчас «Redis недоступен» диагностируется по вторичному симптому (всплеск 409), а не прямо.

## G-09. `Reserve` при ошибке Redis отдаёт 409, неотличимый от реального дубля

**Суть.** Если `store.Reserve` вернул ошибку (Redis недоступен), middleware отвечает `409 REQUEST_IN_FLIGHT` — тем же кодом, что и для реального параллельного дубликата. Клиент не может отличить «твой запрос уже обрабатывается» от «хранилище идемпотентности сломалось». Это fail-closed (лучше, чем пропустить дубль), но диагностически вредно и мешает клиентской retry-логике.

**Место.** `internal/transport/http/gin/idempotency_middleware.go:86-93`.

**Подробное описание.**

```go
reserved, err := store.Reserve(c.Request.Context(), key)
if err != nil {
    c.JSON(http.StatusConflict, ErrorResponse{
        Code:    "REQUEST_IN_FLIGHT",
        Message: "a request with this idempotency key is already being processed",
    })
    c.Abort()
    return
}
```

Поведение при недоступном Redis: **все** write-запросы получают 409 с сообщением про «уже обрабатывается». Оператор, глядя на метрики, видит всплеск 409 (которые в F-15 к тому же схлопнуты в общий `error`) и делает вывод о дубликатах/атаке, тогда как причина — лежащий Redis. Клиент с корректной retry-логикой на 409 «подожди и повтори» будет повторять бессмысленно.

Fail-closed сам по себе правильный выбор (пропустить запрос без резервации = риск двойного списания). Проблема только в коде/сообщении.

**Предлагаемый багфикс.** Отдавать 503 с отдельным кодом при инфраструктурной ошибке:

```go
if err != nil {
    c.JSON(http.StatusServiceUnavailable, ErrorResponse{
        Code:    "IDEMPOTENCY_STORE_UNAVAILABLE",
        Message: "idempotency store temporarily unavailable, retry later",
    })
    c.Abort()
    return
}
```

503 корректно сигналит «повтори позже» и отделяется в метриках от 409-дублей. Инвариант fail-closed сохраняется (запрос не пропущен).

**Комментарий.** Связано с F-15 (4xx/5xx схлопнуты) и G-08 (нет PING). Мелкий, но улучшает диагностируемость инцидента с Redis на порядок.

## G-10. `PendingCount` реального consumer = деструктивный `Stats().Lag`

> **⇔ Дубль. Канонично: [F-08](F-operations-observability.md). В итоговом счёте учитывается один раз под F-08.** Тот же дефект (`consumer.go:110-117`, деструктивный `Stats().Lag`), угол раздела G — значимость недостоверного «pending» при решении о replay. Независимым дефектом не считается.

**Суть.** Дубль-подтверждение F-08 из перспективы DLQ/consumer. `Consumer.PendingCount()` возвращает `reader.Stats().Lag`, а `Stats()` в `kafka-go` — snapshot-since-last-call: значения обнуляются при чтении. Любой второй потребитель `PendingCount` (или сам `bulk/wake`) получит искажённое значение.

**Место.** `internal/adapters/kafka/consumer.go:110-117`.

**Подробное описание.** См. F-08 для полного разбора семантики `Stats()`. Здесь важно DLQ-следствие: если оператор через `bulk/wake` смотрит «сколько осталось» для решения о replay или масштабировании, показание недостоверно — особенно если метрики Prometheus тоже дергают `Stats()` (конкурентное потребление одного деструктивного счётчика). Дополнительно `Lag` не включает сообщения в DLQ-топике: «pending» не отражает накопившийся долг в DLQ (G-11).

**Предлагаемый багфикс.** Как в F-08: не использовать `Stats().Lag` как источник истины. Для лага — считать через `kafka-go` `ReadLag(ctx)` (не деструктивно) или через отдельный admin-запрос offset'ов; для DLQ-глубины — отдельная метрика по `bulk.tasks.dlq`.

**Комментарий.** Осознанно оставлен как отдельный пункт (а не только ссылка на F-08), потому что в контексте DLQ/replay «сколько ещё» — операционно значимая величина при принятии решения о проигрывании, и её недостоверность здесь дороже.

## G-11. DLQ-топик без ретеншена/алерта: долг копится молча

**Суть.** `bulk.tasks.dlq` создаётся (`topics.go:44`), сообщения туда пишутся, но нет ни метрики глубины DLQ, ни алерта на её рост, ни политики ретеншена в конфиге топика. Упавшие заказы оседают в DLQ, и об этом никто не узнает, пока клиент не пожалуется.

**Место.** `internal/adapters/kafka/topics.go:14,44`, отсутствие метрик/алертов (связь с F-06, F-10).

**Подробное описание.** DLQ имеет смысл только с наблюдаемостью: рост DLQ = деньги/заказы, застрявшие без обработки. В текущем виде:

- нет счётчика `dlq_messages_total` (F-06 — нет метрик исходов саги вообще);
- нет алерта на `dlq_depth > 0` (F-10 — алертов нет);
- ретеншен топика не задан в `topics.go` (структура `TopicConfig` содержит только `Name`/`Enabled`) — при дефолтном ретеншене Kafka старые упавшие заказы могут быть удалены брокером до того, как их переиграли.

Последнее особенно опасно: DLQ задуман как «с��хранить для replay», но без явного длинного ретеншена сообщения могут исчезнуть по времени.

**Предлагаемый багфикс.**

1. Метрика `dlq_messages_total{reason}` инкрементируется в `publishDLQ`.
2. Метрика глубины `dlq_depth` (периодический замер лага DLQ-топика) + алерт `dlq_depth > 0 for 5m`.
3. Явный длинный ретеншен для DLQ при создании топика (расширить `TopicConfig` полем `RetentionMs`, для DLQ — недели/месяцы).

**Комментарий.** Прямое продолжение F-06/F-10 применительно к DLQ. Без этого DLQ — не «сеть безопасности», а тихая свалка: сообщения туда попадают, но сигнала о том, что пора реагировать, нет.

## G-12. `Producer.Publish` без ключа партиции: нет гарантии порядка

**Суть.** `Producer.Publish` пишет `kafka.Message` без `Key`, с балансировщиком `LeastBytes`. Сообщения одного логического потока (например, все элементы одного batch, или события одного barcode) распределяются по партициям произвольно, без гарантии порядка. Для `bulk.result` и `barcode.edited` это может привести к обработке событий не в том порядке, в котором они произошли.

**Место.** `internal/adapters/kafka/producer.go:44-52` (нет `Key`), `:33` (`Balancer: &kafka.LeastBytes{}`).

**Подробное описание.**

```go
return p.writer.WriteMessages(ctx, kafka.Message{
    Topic: topic,
    Value: body,
    // Key отсутствует
})
```

Без `Key` балансировщик кладёт сообщения в партиции по объёму (`LeastBytes`), не по логическому ключу. Последствия зависят от потребителя:

- `bulk.result`: если результаты одного batch потребляются с расчётом на порядок — нарушится.
- `barcode.edited`: два быстрых редактирования одного barcode могут прийти consumer'у в обратном порядке → History применит их не по времени, «последнее» значение окажется старым.
- DLQ: порядок упавших сообщений теряется (менее критично).

Порядок в Kafka гарантируется только **внутри партиции**, а попадание в партицию определяется ключом. Нет ключа — нет гарантии.

**Предлагаемый багфикс.** Передавать логический ключ партиционирования:

```go
func (p *Producer) Publish(ctx context.Context, topic string, key string, payload any) error {
    body, err := json.Marshal(payload)
    if err != nil { ... }
    return p.writer.WriteMessages(ctx, kafka.Message{
        Topic: topic,
        Key:   []byte(key), // barcodeID для edited, batchID для bulk.result
        Value: body,
    })
}
```

и с `Balancer: &kafka.Hash{}` (партиция по хешу ключа). Для `barcode.edited` ключ — `barcodeID` (все правки одного barcode в одну партицию → строгий порядок); для `bulk.result` — `batchID`.

**Комментарий.** Низкая критичность, потому что зависит от того, полагаются ли потребители на порядок (внешние сервисы вне репозитория). Отмечаю как риск: если History применяет `barcode.edited` без версионирования (см. B-раздел про версии событий), отсутствие порядка = потенциально устаревшее итоговое состояние. Связано с B (нет `eventId`/версии в событиях): порядок + версия — два независимых способа защититься от reordering, сейчас нет ни одного.

## Что проверено и дефектом не является

**`Reserve` через `SET NX` — корректная атомарная резервация.** `SetArgs{Mode:"NX", TTL:...}` компилируется в один `SET key val NX EX` — атомарно, гонки между `Get` и `Reserve` нет на уровне самой резервации (двойная проверка `Get`→`Reserve`→`Get` в middleware обрабатывает проигравшего в гонке корректно). Дефект не в атомарности `Reserve`, а в TTL (G-02).

**`inFlightMarker = "\x00"` — корректно отличается от JSON.** Валидный JSON-ответ не может начинаться с нулевого байта, поэтому коллизия маркера с реальным телом невозможна. Проверено.

**`Producer` с единственным shared `Writer` — правильно.** Комментарий про переиспользование пула TCP верен; `kafka.Writer` потокобезопасен. Здесь дефекта нет (в отличие от Redis-клиентов, которые зачем-то продублированы — G-08).

**Graceful shutdown продюсера.** `Producer.Close()` существует и вызывается при shutdown (проверено в wiring). Буферы сбрасываются. Дефекта нет.
